# 局域网协议

本文描述和鸣 1.5.0 使用的协议 v1。实现入口为 [`lib/networking`](../lib/networking)、[`SessionController`](../lib/session/session_controller.dart) 和[原生音频引擎](../packages/heming_audio/src/heming_audio.cpp)。产品操作规则见[产品规格](v1-spec.md)。

## 通道与发现

| 通道 | 实现 | 地址及用途 |
| --- | --- | --- |
| 发现 | DNS-SD / IPv4 mDNS | `_heming._tcp.local`，UDP 5353，组播 `224.0.0.251` |
| 控制 | WebSocket / JSON | `ws://<IPv4>:<port>/heming`，默认端口 19786 |
| 音频 | 原生 TCP | 每个任务分配端口，从机按块拉取 PCM |
| 校时 | 原生 UDP 单播 | 使用与该任务 TCP 相同的端口号 |

控制端口被占用时使用其他可用端口，界面显示实际值。每台设备保留自己的控制监听器，以支持主控移交。手动输入的主机名解析为 IPv4；当前没有 IPv6 音频通道。

发现回应包含 PTR、SRV、TXT、A 记录，TXT 提供协议版本、设备 ID、名称、成员数及锁定状态。约每 5 秒查询和公告，过期记录清理，退出时发送 TTL 为 0 的撤销公告。发现只是提供加入入口，加入仍需主控接受；组播不可用时可手动输入地址。

网卡列表在周期刷新时更新。应用回到前台或手动刷新设备页时重新绑定发现 socket，以恢复休眠或网络切换后的发现能力；不会重建音频任务。成员回连地址取自实际控制连接的远端地址。

这是满足当前应用需要的精简 DNS-SD 实现，并未提供完整 Bonjour 缓存、跨响应记录拼接或全部名称冲突协商行为。不能仅依据“使用 mDNS”推断它具备完整 Bonjour 兼容性。

## 身份与安全边界

- 设备 ID 持久保存。建立或移交播放组时生成新的 128 位随机会话 ID；每首歌曲使用新的 128 位随机任务 ID。
- 主控将成员身份绑定到已接受的控制连接，不信任消息中自报的其他成员 ID。
- 从机只接受当前主控连接和会话的指令。READY、START、STOP 等任务消息必须与当前任务匹配。
- 主控移交使用一次性随机迁移凭证，只允许指定成员加入指定的新会话；不做故障后的自动选主。
- 原生音频连接绑定会话和任务。切歌关闭旧连接、清空旧缓存，不能继续使用旧数据流。

当前控制与音频传输均未加密，没有 TLS、账号体系或互联网中继。设备发现、随机 ID 和原生握手用于隔离任务与避免串线，不构成面向不可信网络的完整身份认证。使用范围是用户信任的同一局域网。

## 控制消息

每条消息是一个 WebSocket 文本帧，内容为 JSON 对象，必须包含 `v: 1` 和字符串 `type`。接收端限制 `String.length <= 65536`，即最多 65,536 个 UTF-16 code unit，而不是 65,536 个 UTF-8 字节。格式损坏或不支持的协议版本会关闭连接。音频采样不进入该通道。

```json
{"v":1,"type":"ready","sessionId":"<session-id>","taskId":"<task-id>"}
```

| 消息 | 方向 | 行为 |
| --- | --- | --- |
| `join` | 申请者 → 主控 | 提交设备 ID、名称、平台、控制端口和输出设置 |
| `pending` | 主控 → 申请者 | 等待接受，尚未成为参与成员 |
| `welcome` | 主控 → 成员 | 确认会话、主控、成员快照及当前播放模式 |
| `rejected` | 主控 → 申请者 | 返回拒绝、组满或成员锁定等原因 |
| `members` | 主控 → 成员 | 同步成员、READY 集合和输出设置 |
| `reset_task` | 主控 → 成员 | 撤销旧任务，提供完整队列并开始新一轮准备 |
| `queue_state` | 主控 → 成员 | 更新队列展示和待生效模式，保留当前音频任务 |
| `prepare` | 主控 → 成员 | 提供任务、当前歌曲展示信息与原生端口 |
| `ready` | 成员 → 主控 | 本机输出、缓冲、校时均准备完成 |
| `start` | 主控 → 成员 | 提供主控单调时钟上的未来开始时刻 `startTimeUs` |
| `stop` | 主控 → 成员 | 停止任务、清缓存并返回待命 |
| `master_selected` | 原控制协调者 → 成员 | 用户明确保留本机主控后，解除重新选主要求 |
| `output` / `rename` | 成员 → 主控 | 更新本机输出或名称，由主控广播结果 |
| `takeover_request` | 成员 → 主控 | 申请接管，同一时刻保留一个申请 |
| `handover` | 旧主控 → 成员 | 指定新会话、主控、迁移凭证与成员快照 |
| `rejoin` | 原成员 → 新主控 | 凭有效迁移凭证恢复成员连接 |
| `leave` | 成员 → 主控 | 主动退出，本机先停止，其他成员继续 |
| `removed` / `room_closed` | 主控 → 成员 | 被移出或播放组解散，本机停止并断开 |
| `ping` / `pong` | 双向 | 应用层心跳 |
| `notice` | 主控 → 成员 | 提供操作提示，不作为状态指令 |

资源展示信息不包含主控的磁盘路径。成员不会通过控制连接获取主控的资源库或原始文件。

## 准备与开始

1. 待命时，主控可接受加入申请。每组最多 6 台设备，包含主控；未审批申请不计入参与者。
2. 目标歌曲通过规格和文件可读性检查后，建立任务并锁定参与者集合。此时拒绝尚未审批的申请。
3. 主控准备本机输出与约 5 秒 PCM，短曲准备至文件末尾；随后发送 `prepare`，从机拉取音频并校时。
4. 当前参与者全部 READY 后，主控发布未来约 1.5 秒的共同开始时刻。主控也通过原生预约接口开始输出。
5. 切歌生成新任务，再次验证资源并经过完整 READY 屏障；期间持续锁定成员。
6. 队列结束或用户结束播放后，所有端清缓存、返回待命并重新开放加入。

同步播放没有暂停续播、拖动进度、快进或快退消息。资源库的[本机试听](audio-engine.md#本机试听)是独立功能，不采用这组同步控制消息。

## 队列与切歌

开始播放时，取当前可播放条目的有序快照；后续新转换的歌曲不会插入本次队列。每首开始前重新检查文件。直接选择不可播放条目不会中断当前有效播放。

`reset_task` 与 `queue_state` 使用以下字段：

| 字段 | 含义 |
| --- | --- |
| `queue` | 歌曲数组，每项仅包含 ID、标题、时长 |
| `queueIndex` | 从零开始的当前索引 |
| `playbackMode` | 待生效模式：`sequential` 或 `random` |
| `activePlaybackMode` | 当前播放路线实际使用的模式 |
| `skippedCount` | 建立队列时跳过的不可播放条目数 |
| `queueRevision` | 单调递增的队列修订号 |

从机丢弃其他会话或旧修订号的快照，`queue_state` 还须匹配当前任务。未提供队列的旧版消息可回退显示当前单曲。发送前检查队列与当前曲目信息的序列化大小并预留协议字段空间；超限时提示拆分分组，保留原有播放。

默认顺序播放。修改模式只更新待生效值，当前歌曲继续；下一首或直接点选歌曲时才应用新模式。上一首保持当前生效模式。

- **顺序播放**：从选中位置向后进行；上一首可返回队列前一项，包括本轮开始位置之前的歌曲。
- **随机播放**：从本轮未播放的歌曲中抽取；上一首沿实际播放历史返回，再点下一首可沿历史前进。
- 两种模式都在本轮完成后结束，不自动循环。直接选曲或模式变更产生的新播放路线会替换原有前进历史。
- 只有主控可以切歌和修改模式，从机显示相同队列及当前条目。

切歌事务在异步资源检查前废弃旧任务状态，再停止旧音频、验证新资源、重新准备。原生状态采样携带采样时的任务 ID，旧任务迟到的完成或失败不能推进新队列。音频焦点租约跨曲目保留，整次播放结束或退出播放组后释放。

## 主控移交

移交先停止旧任务并清缓存，再保留成员、声道、音量和静音设置。新主控等待成员完成 WELCOME 握手后，才能选择新资源；不会续播旧主控的歌曲。

新主控监听器可能先接受连接，稍后才处理 HANDOVER，因此成员会在有限窗口内重试“目标尚未升为主控”的拒绝。重试只指向指定的新主控和会话。关闭旧控制连接前先发送已排队的停止与移交消息。

加入和移交绑定本机连接操作代次。退出或开始新连接后，旧握手、停止回调和迁移计时器的迟到结果不能覆盖新状态。

## 超时与中断

| 参数 | 当前值 | 行为 |
| --- | --- | --- |
| 应用心跳间隔 | 2 秒 | 发送 `ping` / `pong` |
| 应用心跳超时 | 7 秒 | 检测主控失联后，本机停止并断开 |
| 准备超时 | 25 秒 | 结束准备并提示未就绪设备；从机超时退出 |
| 未审批申请有效期 | 60 秒 | 拒绝过期申请，可重新申请 |
| 移交重连窗口 | 约 7 秒 | 移除未重连成员 |
| WebSocket 建连超时 | 5 秒 | 返回连接失败；主机名解析不包含在该计时内 |

回到桌面、锁屏和普通音频焦点变化不发送 STOP 或 LEAVE，也不改变任务 ID、成员锁定或 READY 规则。焦点竞争只临时降低或静音本机输出，音频消费与时间轴继续推进。临时输出系数和用户音量、静音设置相互独立。

永久焦点丢失后的自动恢复采用保守判断：能够识别外部播放器且确认其停止后才重新申请；无法确认或再次竞争时，保持静音并提供“恢复本机声音”。恢复只能作用于当前有效任务。

从机发生输出设备变更、硬件故障、系统真实休眠或缓冲耗尽时，先停止本机并退出，其他成员继续。主控发生这些中断时广播带 `masterSelectionRequired: true` 的 STOP，全组待命；用户明确继续使用原主控或完成接管后才允许重新播放。普通网络断开依赖连接关闭或心跳检测，因此停止传播存在检测延迟。

## 原生 TCP PCM 格式

整数头字段使用大端序。PCM 为 little-endian signed 16-bit、48,000 Hz、双声道交错样本，每帧 4 字节。单次最多请求 4,800 帧，即 100 ms；接收端在约 5 秒环形缓冲有空间后才继续拉取。

| 帧 | 长度 | 字段顺序 |
| --- | --- | --- |
| 客户端 hello | 24 字节 | magic `0x484D5031` u32、version u32、会话 fingerprint u64、任务 fingerprint u64 |
| 主控 reply | 16 字节 | 总帧数 u64、采样率 u32、声道数 u32 |
| 客户端 pull | 12 字节 | 下一帧位置 u64、请求帧数 u32 |
| 主控 data | 12 字节 + PCM | 样本位置 u64、实际帧数 u32、`实际帧数 × 4` 字节 PCM |

每个接收者使用独立的原生解码与供数流。pull 必须从连续位置读取，不能用于跳转进度；无效规格、数量、位置或不完整数据会使任务失败。末尾返回零帧表示 EOF。

原生 fingerprint 为字符串 ID 的 FNV-1a 64 位值，用于匹配任务，不是密码学认证。最多 5 个通过握手的音频接收者；握手中的连接还有独立的数量和超时限制。

两端 TCP socket 启用 `TCP_NODELAY`。每块响应的 12 字节头和 PCM 合并交给发送函数，减少小块传输等待；TCP 仍是字节流，不保证一个调用对应一个网络包。真实缓冲耗尽会中断，不重复旧样本或累积延迟以掩盖供数不足。

## 原生 UDP 校时和输出

请求为 32 字节：与 TCP hello 相同的 magic、version、会话和任务 fingerprint，后接发起者单调时钟 `t1`。主控返回 48 字节，追加接收时刻 `t2` 和发送时刻 `t3`；从机本地记录接收时刻 `t4`。时间单位为微秒。

```text
RTT = (t4 - t1) - (t3 - t2)
masterOffset = ((t2 - t1) + (t3 - t4)) / 2
```

每轮取 8 次测量中最低的有效 RTT。初次没有有效结果或最佳 RTT 超过 100 ms 时，不报告 READY。播放期间约每 3 秒重新测量并平滑更新映射；明显偏差或持续失败会停止播放。线性重采样的漂移修正限制在 ±500 ppm。

Android 使用 AAudio 呈现时间戳；Windows 使用 IAudioClock 的设备位置和 QPC 时间戳估计实际输出时刻。预约开始和微量速率修正在原生回调中执行。路径补偿与诊断字段见[原生音频引擎](audio-engine.md)。

共同时间轴不能证明扬声器已达到 5 ms 同步：驱动、设备输出和声学传播仍需外部测量。
